# 固件架构设计 — ESP32-S3 + HS-S62A-PL RFID 采集器

> 面向"高实时 + 高稳定"要求的产线固件骨架。
> 相关文档：[BRINGUP.md](BRINGUP.md) 上电排查手册 ｜ [../lib/YFROBOTRFIDI2C/PATCHES.md](../lib/YFROBOTRFIDI2C/PATCHES.md) 库补丁记录

---

## 1. 设计目标与硬约束

| 项 | 值 | 来源 |
|---|---|---|
| 主控 | ESP32-S3 双核 Xtensa LX7 @240 MHz | 板卡定义 |
| 内存 | 320 KB SRAM + 2 MB PSRAM | `rymcu-esp32-s3-devkitc-1.json` |
| Flash | 8 MB，分区表 `default_8MB.csv` | 同上 |
| 外设 | HS-S62A-PL (MFRC522 / SI522A)，I2C，默认 0x28 | 模块用户手册 V1.1 |
| 模块供电 | 3.3–5 V，感应距离 0–2 cm | 同上 |

**实时性目标**：进卡 → 业务侧收到事件 ≤ 50 ms（P99）。
**稳定性目标**：连续 72 h 运行，零看门狗复位、零漏读、零死机。

这两条目标决定了后面所有取舍：**任何可能无界阻塞的调用都不允许出现在任务路径上**。

## 2. 分层架构

依赖方向严格单向向下，下面三层不知道上面存在。

```
┌──────────────────────────────────────────────────────────────┐
│ 应用层   src/main.cpp                                        │
│  任务编排 · 卡事件状态机 · 门禁判定 · 队列 · 看门狗 · 复位保护  │
└───────────────┬──────────────────────────────────────────────┘
                │ 调用                ▲ CardEvent（队列，值传递）
┌───────────────▼──────────────────────┴───────────────────────┐
│ 设备层   src/rfid_reader.{h,cpp}                             │
│  挂载/寻卡/自愈 · 芯片判活(VersionReg) · 在位检测(WUPA+HaltA)  │
└───────────────┬──────────────────────────────────────────────┘
                │ 调用
┌───────────────▼──────────────────────────────────────────────┐
│ 总线层   src/i2c_bus.{h,cpp}                                 │
│  初始化 · 错误分类 · 物理层恢复(9 clock + STOP) · 统计        │
└───────────────┬──────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│ 芯片驱动 lib/YFROBOTRFIDI2C （已打有界超时补丁）              │
└──────────────────────────────────────────────────────────────┘
```

横切模块：`app_config.h`（全部可调参数）、`app_log.{h,cpp}`（唯一串口出口，互斥保护）。

### 各层职责与禁止事项

| 层 | 职责 | 明令禁止 |
|---|---|---|
| 总线层 | 收发字节、错误码语义化、总线自愈 | 不得出现器件语义（不能知道 0x37 是版本寄存器） |
| 设备层 | 器件语义（挂载/寻卡/在位/自愈） | 不得创建任务、不得做 IO 决策 |
| 应用层 | 任务、队列、业务判定 | 不得直接操作 `Wire` |

## 3. 任务划分

```
Core 1 (APP CPU)                          Core 0 (PRO CPU)
├─ rfidTask   prio 6  栈 4096             └─ reportTask prio 3  栈 6144
│   I2C 的唯一持有者                            业务处理 / 上报 / 执行器
└─ healthTask prio 2  栈 3072
    只读统计量，绝不碰 I2C

  loopTask   prio 1  （Arduino 宿主任务，保留，只做 1 s 一次的惰性巡检）
```

| 任务 | 核 | 优先级 | 栈 | 周期 | 单次阻塞上限 | 职责 |
|---|---|---|---|---|---|---|
| `rfidTask` | 1 | 6 | 4096 B | 30 ms | ≈15 ms | 寻卡、去抖、投递事件、链路自愈 |
| `reportTask` | 0 | 3 | 6144 B | 事件驱动 | 无限（仅此处允许） | 串口/MQTT/继电器等一切对外动作 |
| `healthTask` | 1 | 2 | 3072 B | 1000 ms | < 1 ms | 健康度、栈水位、堆水位上报 |
| `loopTask` | 1 | 1 | 8192 B | 1000 ms | 1 ms | 预留 OTA / 按键 / 指示灯 |

### 为什么这样分核

- **采集独占 Core 1**：WiFi/BLE 协议栈固定在 Core 0 且优先级 18–23。把 I2C 采集放在 Core 0，会被协议栈的长临界区穿插，最坏抖动不可预测。分核后采集的抖动只受同核的 `healthTask`（优先级更低）影响。
- **`reportTask` 独占 Core 0**：一切对外 IO（将来接 MQTT/HTTP）都可能阻塞数百毫秒，放在 Core 1 会直接打乱采集节拍。
- **优先级只分三档**：档位越多越容易出现优先级反转和饥饿。这里只要保证"采集 > 业务 > 巡检"即可。

## 4. 并发与 IPC

### 4.1 单写者原则（核心）

**全进程只有 `rfidTask` 调用 I2C 收发。** 这带来三个直接好处：

1. 热路径上**不需要任何锁**，没有锁就沒有优先级反转和死锁。
2. `Wire` 本身不是线程安全的（厂商库也不做保护），单写者让这个隐患直接消失。
3. 采集时序完全确定，不受其它任务调度影响。

`healthTask` 需要总线信息时，只读 `i2cbus::diag()`（纯统计量），不发 I2C。

### 4.2 事件队列

| 项 | 值 |
|---|---|
| 类型 | `CardEvent`（定长 POD，含 UID/时间戳/在位时长，约 32 B） |
| 深度 | 8（`CFG_Q_CARD_LEN`） |
| 投递方式 | `xQueueSend(..., 0)` 非阻塞 |
| 满载策略 | **丢弃并计数**，绝不阻塞采集任务 |

> 设计取舍：采集的实时性优先级高于"一条事件都不丢"。门禁场景下卡事件是可重入的——
> 卡还在场上就会被反复读到，丢一条不影响正确性；但采集任务被阻塞 30 ms 会直接
> 打乱整个节拍。若将来换成"必须一条不丢"的计费场景，请改为加长队列 + 落 NVS，
> 而不是改成阻塞投递。

### 4.3 日志

`appLogLine()` 内建互斥锁（带优先级继承），格式化 + 写出是原子的。
Arduino-ESP32 的 `Serial(HWCDC)` 并发 `printf` 会互相踩缓冲，输出串行错行，
所以不允许任何任务直接调 `Serial`。

#### 双通道输出

ESP32-S3-DevKitC-1 上 `ARDUINO_USB_CDC_ON_BOOT=1` + `ARDUINO_USB_MODE=1` 时，
框架的两个对象映射如下（已核对 framework 源码 `HWCDC.h:110-116`、`HardwareSerial.h:329-333`）：

| 对象 | 类型 | 物理口 |
|---|---|---|
| `Serial` | `HWCDC` | 原生 USB 口（`/dev/cu.usbmodem*`） |
| `Serial0` | `HardwareSerial` | **UART0 → GPIO43/44 → 板载 USB-UART 桥** |

`appLogInit()` 按 `CFG_LOG_USB_CDC` / `CFG_LOG_UART0` 两个开关同时打开两路，
内容完全一致。理由很实在：**现场最怕"固件打到了一个同事没接的口上"**，
而这在交接场景里几乎必然发生（对方手边可能只有一个 USB-TTL 模块）。
代价是 Flash +0.7 %，换来"谁接哪个口都能看到"。

两路各自独立、互不阻塞 —— 任何一路写不进去都不会拖住另一路：

- **USB CDC**：必须设 `setTxTimeoutMs()`。`HWCDC::write()` 在主机不在时是
  同步等主机的，`tx_timeout_ms` 就是它的唯一上限（源码里那个
  `tries = tx_timeout_ms` 循环）。没有它，拔掉 USB 线之后一次日志就能把调用
  任务整段阻塞住 —— USB CDC 最经典的坑。本项目取 20 ms。
- **UART0**：把发送缓冲加大到 512 B（`setTxBufferSize()`，**必须在首次 `begin()`
  之前调用才生效**），115200 下一行最长约 200 B 的日志排得进缓冲，基本不阻塞。

#### 输出分级（面向"同事拿着板子测"）

| 级别 | 内容 | 周期 |
|---|---|---|
| `SELF` | 启动硬件自检结论（引脚四态 + 锡桥） | 仅启动一次 |
| `CARD` | 刷卡事件，用 `>>>` / `<<<` 做视觉锚点 | 事件驱动 |
| `STATE` | 一行状态：运行时长 / 进卡离卡拒绝丢弃计数 / 链路 | `CFG_STATE_LINE_MS`（10 s） |
| `WARN` | 栈水位、堆、队列溢出等异常 | 仅越门限时 |
| `HEALTH` | 全量诊断（栈水位、堆、总线直方图） | 仅 `CFG_VERBOSE_HEALTH=1` 时 |

**设计意图：健康时保持安静。** 这样"日志里出现 `WARN`"本身就是有意义的信号，
不会被每秒三行的日常输出冲淡。研发阶段把 `CFG_VERBOSE_HEALTH` 置 1 即可拿回全量诊断。

> ⚠️ 这里有一个必须记住的耦合陷阱：`healthTask` 的**循环周期**兼任喂看门狗，
> 而**状态行打印周期**只是日志。早期版本两者共用 `CFG_HEALTH_PERIOD_MS`，
> 把它调大到 10 秒就会让任务先被 5 秒的看门狗复位掉。
> 现已拆成 `CFG_HEALTH_TICK_MS`（喂狗，必须远小于 `CFG_TWDT_SECONDS`）
> 与 `CFG_STATE_LINE_MS`（打印，多长都行）两个独立常量。

## 5. 时序预算（100 kHz I2C）

单字节在线上 ≈ 9 bit ÷ 100 kHz ≈ 90 µs；一次"写寄存器"（地址+寄存器+数据）≈ 3 B ≈ 270 µs；
一次"读寄存器"（先写地址再读回）是两次事务 ≈ 600 µs。

| 动作 | 组成 | 耗时 |
|---|---|---|
| 地址探测 `probe()` | 1 字节 | ≈ 0.1 ms |
| `ReadVersion()`（链路判活） | 读 1 寄存器 | ≈ 0.6 ms |
| `WUPA`（唤醒） | ~6 写 + 1~3 读 | ≈ 2–3 ms |
| `SELECT`（防冲突+选卡） | 含 CRC 计算，约 10 次寄存器访问 | ≈ 4–6 ms |
| `HaltA` | 2 写 + 1 读 | ≈ 1 ms |
| **一次"有卡"轮询合计** | | **≈ 8–10 ms** |
| **一次"无卡"轮询合计** | 卡在 RC522 内部定时器上（`CFG_RC522_TRELOAD`=512 → 12.8 ms） | **≈ 12.8 ms** |

**进卡识别延迟** = 剩余轮询等待（0 ~ 30 ms） + 单次寻卡（≈10 ms）
→ **P50 ≈ 20 ms，P99 ≈ 45 ms**，满足 ≤50 ms 目标。

> 注意：**"无卡"比"有卡"更慢**。因为无卡时程序要等 RC522 自己的定时器超时，
> 这段时间是纯 I2C 空转。这就是把 `TReloadReg` 从默认 25 ms 改成 12.8 ms 的原因。
> 若现场偶发漏读弱卡，把 `CFG_RC522_TRELOAD` 调回 1000 会显著降低灵敏度损失，
> 代价是采集周期从 30 ms 拉长到 45 ms。

**需要更快？** 把 `CFG_RFID_POLL_MS` 调到 15、`CFG_RC522_TRELOAD` 调到 256（≈6.4 ms），
并把 `CFG_I2C_FREQ_HZ` 提到 400000。此时单次轮询 ≈ 3 ms，识别延迟 P99 ≈ 20 ms。
前提是总线已加 4.7 kΩ 外部上拉（见 BRINGUP.md）。

## 6. 故障模型与对策

| # | 故障 | 现场表现 | 本架构的对策 | 代码位置 |
|---|---|---|---|---|
| 1 | 模块上电时序异常（厂商库 README 已记录的已知问题） | 上电后完全无应答，断电重启才恢复 | 有界初始化（最长 100 ms）→ 判活失败 → 自动自愈重挂载，不死循环 | `rfid::begin/heal`、库 PATCH-1 |
| 2 | 从机在传输中途被复位，SDA 被永久拉低 | 所有事务 `endTransmission()==5` | 物理层恢复：9 个时钟 + STOP，把从机顶出死锁 | `i2cbus::recover` |
| 3 | 模块掉线 / 排线松动 | 读卡突然全失败 | 每轮做链路探针（浅检地址 + 周期深检 VersionReg），连续 5 次失败才判掉线并触发自愈 | `rfid::poll`、`rfid::linkState` |
| 4 | 任务卡死（库内死循环 / 硬件等待） | 设备"假活"，不再读卡也不重启 | 任务看门狗（TWDT）+ `panic=true`，超时打印回溯并复位 | `main.cpp` |
| 5 | 启动即崩 → 复位风暴 | 串口反复打印启动横幅 | RTC 域断连续复位计数，达到阈值进**安全模式**（只自检不跑业务），保住串口可诊断 | `countBootAndLog` |
| 6 | 供电跌落（天线启动瞬间电流冲击） | 随机重启 | 启动横幅打印 `reset_reason`，`BROWNOUT` 可一眼定位；架构上预留 `VCC` 负载开关 | `resetReasonName` |
| 7 | 事件队列溢出 | 业务侧丢事件 | 计数并丢弃，采集侧绝不阻塞 | `rfidTask` |
| 8 | 堆碎片（自愈路径会 malloc/free） | 运行数天后分配失败 | 巡检任务持续上报 `getMinFreeHeap()`，min 值下探即为前兆 | `healthTask` |
| 9 | 读卡误触发（卡在读卡边缘抖动） | 同一次刷卡上报多条 | 卡离开需连续 500 ms 无应答才判定离场 | `CFG_CARD_RELEASE_MS` |
| 10 | **模块长期缺席**（接线没弄好 / 没装模块） | 日志被"自愈失败"刷屏，总线被以 30 ms 节奏反复刷 | 链路不可用时走指数退避（250 ms → 10 s 封顶），日志同条节流 5 s，并在状态变化沿立即打印 | `rfidTask` 路径 A |
| 11 | **SDA/SCL 接反** | 电平/上拉/波形全正常，错误码清一色 NACK，全总线无应答 —— 极易误判为"模块坏了" | bring-up 固件第 3 步自动互换扫描；`diagnose()` 把"接反"列为全 NACK 场景的第一嫌疑 | `bringup/main.cpp`、`i2cbus::diagnose` |

### 6.1 链路三态与退避恢复

采集任务有两条**互斥**路径，由 `rfid::linkState()` 的三态驱动：

| 状态 | 含义 | 恢复动作 | 代价上界 |
|---|---|---|---|
| `UP` | 已挂载且链路健康 | 无，正常 30 ms 轮询 | — |
| `LOST` | 曾挂载成功，现在掉线（地址已知） | `heal()`：物理层 9 时钟解卡 + 完整重初始化 | 3 轮 × (recover + attach + 100 ms) |
| `DOWN` | 从未挂载成功（地址未知） | `retry()`：只试 0x28 / 0x2F，**不做全总线扫描** | ≤2 个 I2C 事务 |

两条路径**共用一条指数退避曲线**：250 → 500 → 1000 → 2000 → 4000 → 8000 → 10000 ms（封顶）。
成功即归零；失败即升级。退避等待期间以 `CFG_BACKOFF_TICK_MS`（50 ms）粒度浅睡，
因此链路恢复的发现延迟上界是 50 ms，而看门狗每 50 ms 被喂一次。

**为什么 `DOWN` 必须走廉价重试而不能复用 `begin()`**：`begin()` 含全总线扫描（112 个地址）。
线路超时的情况下单次重试要吃掉 2 秒以上，退避曲线就失去意义了；
而 `retry()` 的代价是常数级的 2 个事务，这才让"250 ms 起退避"成为可能。

**为什么要退避**：模块缺席是"接线还没弄好"的正常状态，不是故障。
以 30 ms 节奏刷总线既拿不到新信息，又会让真正有用的那一行日志被淹没 ——
现场看到的"持续刷屏 + 反复自愈失败"就是这么来的。

### 6.2 诊断函数必须只看"本次探测"

`i2cbus::diagnose()` 的签名是 `diagnose(const ErrTally &t)`，**纯函数**，
只吃"这一次探测的错误码分布"，绝不读累计统计。这是踩过坑之后定的规矩：

> bring-up 固件第 3 步（引脚互换测试）用**另一套引脚配置**扫到了一个设备，
> 于是全局统计里 `ok` 变成 1。此后所有"从未有人应答"的判据（`tx>0 && ok==0`）
> 全部失效，`diagnose()` 在整整 451 次 NACK 面前给出了"总线通信正常。"的结论，
> 而实际操作员看到的是四个字 —— 与现场完全矛盾。

**结论**：跨状态聚合的计数器不能用来做诊断。诊断必须是"本次证据"的纯函数，
这样这类错误从结构上不可能再发生。

### 6.3 关于自愈路径的 malloc

`Wire.end()` 会 `free()` 两个 128 B 缓冲，`Wire.begin()` 再 `malloc()` 回来
（framework `Wire.cpp` 实测行为）。因此每次自愈会产生 2 次 malloc + 2 次 free。

- 触发条件苛刻：**连续 5 次链路判活失败**，正常运行下永不触发。
- 风险已闭环：`healthTask` 每秒上报堆峰值水位，碎片化会先于故障暴露出来。
- 若产线需要 7×24 零堆分配，可改为**用负载开关对模块 VCC 做硬复位**（见 8.1），
  那样连总线恢复都不必做。

### 6.4 硬件层面的两条强建议

1. **给模块 VCC 加一路 MOS 负载开关**（如 AO3401 + 一个 GPIO 控制）。
   这是唯一能 100% 治本"上电时序异常"的手段 —— 软件软复位救不回来的场合，
   固件拉低 200 ms 再上电即可，等价于"拔插一次电源"。
2. **SDA/SCL 各加 4.7 kΩ 上拉到 3.3 V**。
   RC522 模块板载通常不带外部上拉，只靠 ESP32 内部 ~45 kΩ。
   在 100 kHz 下边沿已经吃紧，排线一长就会出现"时好时坏"。
   加的电阻不需要去掉——它只会让波形更干净。

| 项 | 方法 | 通过判据 |
|---|---|---|
| 冷启动挂载 | 断上电 20 次，每次看启动日志 | 20/20 一次挂载成功，无自愈 |
| 持续读卡 | 同一张卡持续贴近 72 h | 无重启（`reset_reason` 仅 POWERON）、无漏报 |
| 快速刷卡 | 手动连续刷卡 200 次 | 上报次数 = 刷卡次数，无重复无遗漏 |
| 拔插排线 | 带电拔掉模块 SDA，30 s 后插回 | 退避封顶 10 s + 浅睡 50 ms，故 ≤11 s 内自动恢复读卡（日志出现 `链路恢复`） |
| 排线长断 | 拔掉模块 SDA 后**不再插回**，观察 10 min | 日志按指数退避收敛到每 10 s 一行；总线事务数不再增长（`tx` 只随重试线性上升，不是每秒 33 次） |
| 总线拉死 | 断开模块 VCC 再上电 | 自动走自愈并恢复，无复位 |
| 看门狗有效性 | 临时在 `rfidTask` 里 `while(1);` | ≤5 s 触发 TASK_WDT 复位（退避路径 50 ms 浅睡，不会饿死 WDT） |
| 复位循环保护 | 临时在 `setup()` 开头强制复位 | 第 8 次进入安全模式，不再复位 |
| 弱卡边界 | 卡放在 2 cm 边缘 | 记录实际识别距离，与硬件标称对比 |
| **引脚接反回归** | 故意把 SDA/SCL 对调后跑 bring-up 固件 | 第 3 步必须报"互换后能扫到设备"；第 4/5 步沿用互换引脚仍能挂载成功；结论区给出正确接法 |

## 9. 已知短板与演进路线

| 短板 | 影响 | 建议 |
|---|---|---|
| 无模块电源硬复位 | 极少数上电异常只能靠人工断电 | 加负载开关（6.4） |
| 无 NVS 持久化 | 白名单变化需重新烧录 | 接 NVS 或后端下发，`isAllowed()` 已是唯一改动点 |
| 无 OTA | 现场升级需拆机 | `loop()` 已预留挂载点，推荐双分区 + 回滚 |
| 无掉电前事件落盘 | 断电容灾场景会丢事件 | 队列溢出计数已就绪，接 NVS 即可 |
| 库仍有 `PCD_WriteRegister` 静默丢错 | 写失败无声 | 已用 `VersionReg` 判活兜底；升级库时按 PATCHES.md 复检 |
| 单一读卡器 | 无冗余 | 若需多读卡器，用 `Wire1`（第二个 I2C 控制器）+ 第二个采集任务，架构不用改 |
